# Building with the kit

Typical end-to-end workflows for the participant journey, in
increasing order of involvement.

## Workflow 1 — Try the bundled mini example

Quickest sanity check. Confirms the kit is installed and runnable
against a 4-candidate toy fixture.

```bash
# 1. Generate predictions
PYTHONPATH=src python3 -m biokg_align_kit run-baseline \
  --data-dir examples/mini \
  --task NCIT-DOID \
  --split valid \
  --baseline hybrid_lexical \
  --output /tmp/mini.tsv

# 2. Validate
PYTHONPATH=src python3 -m biokg_align_kit verify \
  --predictions /tmp/mini.tsv \
  --candidates examples/mini/tasks/NCIT-DOID/valid.cands.tsv \
  --candidates-per-query 0      # mini fixture has 4 candidates, not 50

# 3. Score
PYTHONPATH=src python3 -m biokg_align_kit score \
  --predictions /tmp/mini.tsv \
  --answers examples/mini/answers/NCIT-DOID.valid.answers.tsv
```

The score step emits all three metric families because the mini
fixture ships the `*.preferred.tsv` and `*.graded.tsv` files. On the
perfectly-correct
hybrid_lexical predictions for this toy fixture you should see
`preferred_typed_mrr = 1.0` and `hierarchy_aware_typed_ndcg_at_10
≈ 0.984`.

## Workflow 2 — Sanity-check on the canonical fixture

Confirms the kit produces clean validation against 50-candidate
queries (production shape).

```bash
PYTHONPATH=src python3 -m biokg_align_kit run-baseline \
  --data-dir examples/canonical \
  --task NCIT-DOID \
  --split valid \
  --baseline hybrid_lexical \
  --output /tmp/canonical.tsv

PYTHONPATH=src python3 -m biokg_align_kit verify \
  --predictions /tmp/canonical.tsv \
  --candidates examples/canonical/tasks/NCIT-DOID/valid.cands.tsv
# (no --candidates-per-query flag needed; default 50 matches)

PYTHONPATH=src python3 -m biokg_align_kit score \
  --predictions /tmp/canonical.tsv \
  --answers examples/canonical/answers/NCIT-DOID.valid.answers.tsv
```

The canonical fixture validates without warnings and exercises all
metric families. The fixture is generated by
`examples/canonical/_build_canonical_fixture.py`, which is
deterministic — re-running it produces byte-identical files.

## Workflow 3 — Score your own model against the public data

The standard participant loop after downloading the public data
artifact.

```bash
DATA=~/biokg-align-v0.2.0-public

# 1. Run your ranking model. It must emit a four-column block-format
#    TSV in canonical row order; see documentation/submission_format.md
#    and documentation/block_scoring.md for the exact contract.
python my_model.py \
  --cands $DATA/tasks/NCIT-DOID/valid.cands.tsv \
  --graph $DATA/graph \
  --output predictions.tsv

# 2. Validate. Block-format default; the canonical 50 is enforced.
PYTHONPATH=src python3 -m biokg_align_kit verify \
  --predictions predictions.tsv \
  --candidates $DATA/tasks/NCIT-DOID/valid.cands.tsv

# 3. Score against the public valid split. The kit auto-discovers
#    *.preferred.tsv and *.graded.tsv.
PYTHONPATH=src python3 -m biokg_align_kit score \
  --predictions predictions.tsv \
  --answers $DATA/tasks/NCIT-DOID/valid.cands.tsv
```

Note: the kit's `score` accepts the train/valid `cands.tsv` directly
as the `--answers` argument, because it carries the gold columns
(`TgtEntities`, `Relations`) and the candidate set (`TgtCandidates`)
in addition to `QueryID`. The same code path runs against a private
`answers.tsv` server-side.

For all three tasks together, concatenate (in canonical task order:
NCIT-DOID, SNOMED-FMA, SNOMED-NCIT) and re-run.

## Workflow 4 — Use the Datalog-projected graph

The kit ships a syntactic Datalog reader for participants who want
to consume `graph/facts.dl` and `graph/rules.dl`:

```python
from biokg_align_kit.datalog import load_facts, load_rules

facts = load_facts("graph/facts.dl")    # list[Fact]
rules = load_rules("graph/rules.dl")    # list[Rule]

# Atoms have .predicate (str) and .args (tuple[str, ...])
assert facts[0].atom.predicate in {"subclass", "edge", "equiv", "domain", "range", "inverse", "subprop", "transitive"}
```

The reader is syntax-only — it parses the files into typed Python
structures but does **not** evaluate rules. For closure computation,
pipe the structures into a Datalog engine of your choice (Soufflé,
Clingo, pyDatalog). The released `rules.dl` contains the OWL 2 RL
closure rules used by the organiser pipeline; running these against
the facts reconstructs the inferred hierarchy ELK produces
internally.

## Workflow 5 — Rebuild a graded-relevance file

When you want to verify the released `*.graded.tsv` by reconstruction:

```bash
PYTHONPATH=src python3 -m biokg_align_kit build-graded-relevance \
  --preferred  $DATA/tasks/NCIT-DOID/valid.preferred.tsv \
  --candidates $DATA/tasks/NCIT-DOID/valid.cands.tsv \
  --triples    $DATA/graph/triples.csv \
  --output     /tmp/reconstructed.graded.tsv

diff $DATA/tasks/NCIT-DOID/valid.graded.tsv /tmp/reconstructed.graded.tsv
# Should be empty (byte-identical).
```

## Failure modes worth knowing about

- **`Block-format submission row count mismatch`** — your file has
  the wrong number of rows. Check that you emitted exactly
  `block_size = candidate_count × |relations|` rows per query of
  `cands.tsv`, in cands-row order.
- **`SrcEntity ... does not match the canonical SrcEntity`** —
  your block boundaries don't align with `cands.tsv`'s row order.
  Don't dedupe or sort the submission by source; emit blocks in
  cands-file row order.
- **`Relation 'X' is not in the canonical relation list`** — typo
  or stale relation name. The canonical three are
  `equivalent`, `source_subsumed_by_target`,
  `source_subsumes_target`, exact spelling.
- **Stderr note about missing `*.preferred.tsv`** — only the
  diagnostic family will be reported. The public release ships
  these files; check the path you passed to `--answers`.
- **Score reports `preferred_entity_relation_queries = 0`** — your
  model's top-1 candidate entity is wrong on every query in the
  evaluation set. The metric is unmeasurable on this submission;
  fix the entity ranking before reading anything into the
  relation Macro-F1.

## Reading the metric output

The headline keys in the order they typically matter most:

1. **`preferred_typed_mrr`** — primary leaderboard metric (paper §1.5).
2. **`preferred_typed_hits_at_1`** — strict top-1.
3. **`hierarchy_aware_typed_ndcg_at_10`** — secondary, rewards
   hierarchically-close candidates.
4. **`preferred_entity_relation_accuracy`** — isolates the relation-
   typing sub-problem given a correct entity. Read alongside the
   `*_queries` support.
5. **`diagnostic_*`** keys — kit-only; useful for fast iteration
   but not on the leaderboard.

Always report support counts alongside the headline numbers; a
high score on a tiny support is weak evidence.
