# Building with the kit

Typical end-to-end workflows for the participant journey, in increasing order of involvement.

## Workflow 1 — Try the bundled mini example

Quickest sanity check against a 4-candidate toy fixture laid out like a release.

```bash
PYTHONPATH=src python3 -m biokg_align_kit run-baseline \
  --data-dir examples/mini --task NCIT-DOID --split valid \
  --baseline hybrid_lexical --output /tmp/mini.tsv
PYTHONPATH=src python3 -m biokg_align_kit verify \
  --predictions /tmp/mini.tsv --data-dir examples/mini --split valid
PYTHONPATH=src python3 -m biokg_align_kit score \
  --predictions /tmp/mini.tsv --data-dir examples/mini --split valid
```

`score` prints one line per (task, key) plus the `macro` block. On this toy fixture you should see
`preferred_typed_mrr = 1.0` and `hierarchy_aware_typed_ndcg_at_10 ≈ 0.984`.

## Workflow 2 — Sanity-check on the canonical fixture

The same commands with `--data-dir examples/canonical` exercise the production shape (50 candidates
per query). The fixture is generated by `examples/canonical/_build_canonical_fixture.py`, which is
deterministic (re-running it produces byte-identical files; the graded file is built with the kit's own
`compute_graded_relevance`).

## Workflow 3 — Score your own model against the public data

```bash
DATA=~/BioKG-Align-v0.4.0-public
python my_model.py --data $DATA --split valid --output predictions.tsv   # five columns, all tasks
PYTHONPATH=src python3 -m biokg_align_kit score \
  --predictions predictions.tsv --data-dir $DATA --split valid [--tasks NCIT-DOID]
```

Your model must emit, for every row of every `tasks/<task>/valid.cands.tsv`, one row per
(candidate, relation) with that row's `QueryID` and `SrcEntity` — see
[submission_format.md](submission_format.md). `score` reads the gold from `$DATA/evaluation/` and is
lenient by default: if you score only some queries or tasks you get warnings and per-task
`queries_expected` / `queries_scored`, and the macro covers the tasks with scored queries. Add
`--strict` to apply the platform rules. `--answers $DATA/evaluation/<task>/valid.answers.tsv` scores a
single task against one answers file.

The query mode of train and valid queries is in `evaluation/query_metadata.tsv` (`QueryMode`:
`equivalence` or `subsumption`); it is withheld for test.

## Workflow 4 — Use the Datalog-projected graph

The kit ships a syntactic Datalog reader for participants who want to consume `graph/facts.dl` and `graph/rules.dl`:

```python
from biokg_align_kit.datalog import load_facts, load_program, load_terms

facts = load_facts("graph/facts.dl")    # list[Fact]
program = load_program("graph/rules.dl")
terms = load_terms("graph/datalog_terms.tsv")

# Atoms have .predicate (str) and .args (tuple[str, ...])
assert facts[0].atom.predicate in {"program_seed", "source_triple", "literal_datatype"}
```

The reader is syntax-only — it parses the files into typed Python structures but does **not** evaluate rules. For closure computation, run the released Soufflé program or pipe the parsed structures into a Datalog engine of your choice.

## Workflow 5 — Score OWL 2 RL mapping conflicts

Install Soufflé, then pass the released graph directory to the normal scorer:

```bash
biokg-align-kit score \
  --predictions predictions.tsv --data-dir $DATA --split valid \
  --graph-dir $DATA/graph --conflict-report conflict-report.json
```

The scorer selects the top-ranked mapping for each `QueryID`, evaluates those mappings with `conflict_rules.dl`, and subtracts inconsistencies already derivable from the public graph. It reports `datalog_inconsistency_count`, `datalog_inconsistencies_per_mapping`, and related diagnostics. Omitting `--graph-dir` preserves the existing dependency-free scoring path.

Since v0.3.0 the released disjointness axioms are **certified consistent with the complete reference alignment** (see the data card's reference-consistency curation declaration), so this count is a sound signal: a mapping that induces an inconsistency is not a reference mapping. The conflict count is a diagnostic, never a leaderboard metric.

## Workflow 6 — Rebuild a graded-relevance file

```bash
PYTHONPATH=src python3 -m biokg_align_kit build-graded-relevance \
  --preferred  $DATA/evaluation/NCIT-DOID/valid.preferred.tsv \
  --candidates $DATA/tasks/NCIT-DOID/valid.cands.tsv \
  --triples    $DATA/graph/triples.csv \
  --output     /tmp/reconstructed.graded.tsv
diff $DATA/evaluation/NCIT-DOID/valid.graded.tsv /tmp/reconstructed.graded.tsv
```

The organiser builds the released files with the same function over its ELK-augmented hierarchy; the
public `graph/triples.csv` carries the `subclass_of` edges participants can use.

## Workflow 7 — Verify the real submission shape against the public test candidates

The public `tasks/<task>/test.cands.tsv` files carry `QueryID, SrcEntity, TgtCandidates` and no gold,
so you cannot `score` test locally — but you can, and should, run the platform's rules on your
submission before uploading:

```bash
python my_model.py --data $DATA --split test --output submission.tsv   # all three tasks, one file
PYTHONPATH=src python3 -m biokg_align_kit verify --predictions submission.tsv --data-dir $DATA --split test
# -> Submission validation passed (3 task(s), split test)
```

`verify` is strict: any violation (unknown or missing query, missing or duplicate pair, off-pool
target, bad relation, non-finite score, `SrcEntity` mismatch, wrong header) is an error, exactly as on
the platform. Practise on a fixture: `run-baseline --data-dir examples/canonical --task NCIT-DOID
--split test --baseline random --output /tmp/t.tsv` then `verify --predictions /tmp/t.tsv --data-dir
examples/canonical --split test`.

## Workflow 8 — Coherence checking your mappings (canary individuals)

The released Datalog program is OWL 2 RL: it detects *inconsistency* (contradictory facts), but an unsatisfiable class with no members produces no conflict on its own. You can turn it into a coherence check by giving every class a member. Add one fresh "canary" individual per class, typed at that class; RL type propagation (`cax-sco`, `cax-eqc1/2`) carries each canary up the hierarchy, and any canary that lands in two disjoint classes (`cax-dw`) names its class as unsatisfiable in the released fragment.

On the released facts alone this reports **nothing — by construction**: the fact base is curated so the shipped theory cannot contradict the reference alignment — since v0.3.1 by removing only the minimal clashing fact set (see the data card declaration) — and the build verifies zero witnesses. The check earns its keep on *your* mappings: append your candidate or top-1 mappings as `source_triple` rows, and any canary hit tells you those mappings cross a disjointness boundary that no reference mapping crosses — i.e. something in your set is wrong.

Canary identifiers are free Soufflé symbols — they need no `datalog_terms.tsv` entry. Only the `rdf:type` predicate and the class terms must resolve through the term dictionary, and both already do.

Work on a copy of the released `graph/` directory (the check appends facts):

```bash
cp -r "$DATA/graph" coherence-check && cd coherence-check
python3 - <<'EOF'
import csv
with open("datalog_terms.tsv", newline="") as handle:
    terms = {row["lexical"]: row["term_id"]
             for row in csv.DictReader(handle, delimiter="\t")
             if row["term_type"] == "iri"}
rdf_type = terms["http://www.w3.org/1999/02/22-rdf-syntax-ns#type"]
with open("properties.csv", newline="") as nodes, \
     open("source_triple.facts", "a", encoding="utf-8") as facts:
    for row in csv.DictReader(nodes):
        term = terms.get(row["iri"])
        if term:
            facts.write(f"canary\tcanary:{row['node_id']}\t{rdf_type}\t{term}\n")
EOF
mkdir out
souffle -j 8 -D out conflict_rules.dl
grep "canary:" out/inconsistency.csv | sort -u
```

Each surviving row names an unsatisfiable class directly in its `canary:<node_id>` argument; the first column is the violated rule, and the other term ids decode through the term dictionary:

```bash
grep "canary:" out/inconsistency.csv | cut -f2,3 | tr '\t' '\n' | sort -u \
  | grep -F -f - datalog_terms.tsv
```

On the released graph the `grep` comes back **empty — that is the verified baseline** (the build asserts it). To put the check to work, also append your candidate or top-1 mappings as `source_triple` rows (the same representation `--graph-dir` conflict scoring inserts; see Workflow 5) before running Soufflé: every hit then names a class your mappings make unsatisfiable. When a class is unsatisfiable, every subclass of it is too — expect one hit per affected class, not one per root cause; the rule column plus the decoded class terms point at the offending disjointness.

**Scope — read before citing the result.**

- Since v0.3.0 the released disjointness axioms are certified consistent with the complete reference alignment (data card, reference-consistency curation declaration). A canary hit induced by your mappings is therefore a **sound** wrongness signal: no reference mapping crosses a shipped disjointness boundary. The converse does not hold — a clean run does not make your mappings correct.
- The check covers the subclass / equivalence / disjointness fragment that ships in the fact base — exactly what OWL 2 RL can propagate from a class-level typing. Axioms with existential restrictions in the superclass position (`C ⊑ ∃R.D`, the dominant modelling pattern in SNOMED and NCIT) are outside OWL 2 RL and are excluded from the released facts (they are listed in the release's `reports/unsupported_axioms.csv`, and remain visible quantifier-free as projected edges in `graph/triples.csv`).
- The released fact base is deliberately curated (some upstream disjointness is withheld — see the data card), so neither a clean run here nor one over your mappings certifies coherence under the full source ontologies. For that, load the upstream OWL into a DL reasoner (e.g. ELK).

At release scale expect minutes with `-j 8`, not seconds — the canaries effectively materialise the class hierarchy's transitive closure.

## Failure modes worth knowing about

- **`[header]`** — the file is not `QueryID SrcEntity TgtEntity Relation Score` (tab-separated, in
  that order). A four-column file from an older kit is rejected here.
- **`[unknown_query_id]` / `[missing_query]`** — a `QueryID` is not in the candidate files you
  validate against, or a query has no row. Check that you used the right split and every task.
- **`[off_pool_target]`** — a row names a target that is not in *that query's* pool. The two queries of
  one source have different pools: never copy rows between queries of the same source.
- **`[incomplete_query]` / `[duplicate_pair]`** — a query does not have exactly one row per
  (candidate, relation).
- **`[bad_relation]` / `[bad_score]`** — relation spelling, or NaN/infinite/unparseable scores.
- **Lenient warnings in `score`** — your local numbers used fallbacks; they are not comparable with
  the leaderboard. Run `verify` to see what the platform would reject.
- **`preferred_entity_relation_queries = 0`** — your top-1 entity is wrong on every query; the gated
  relation metric is unmeasurable on this submission.

## Reading the metric output

The headline keys in the order they typically matter most:

1. **`preferred_typed_mrr`** — primary leaderboard metric.
2. **`preferred_typed_hits_at_1`** — strict top-1.
3. **`hierarchy_aware_typed_ndcg_at_10`** — secondary, rewards hierarchically-close candidates.
4. **`preferred_entity_relation_accuracy`** — isolates the relation-typing sub-problem given a correct entity. Read alongside the `*_queries` support.
5. **`diagnostic_*`** keys — kit-only; useful for fast iteration but not on the leaderboard.

Always report support counts alongside the headline numbers; a high score on a tiny support is weak evidence.

## Baseline results

The organiser ships the test predictions of 13 systems under `baseline_predictions/` (run 0 as
`<task>.<name>.tsv`, repeat runs as `<task>.<name>.run<i>.tsv`). The numbers below are the
**v0.4.0-rc1** results on the **private test set**. They are **not comparable with v0.3.x numbers**: v0.4.0 adds
2,752 SNOMED-FMA subsumption-mode queries and changes the query identity and the scoring join.
Stochastic systems were run three times (seeds 20260426–20260428) and are reported as **mean ±
sample standard deviation**; deterministic systems ran once. The macro rows are the mean over runs
of each run's macro across the three tasks. Only `random` and `hybrid_lexical` are reproducible with
this kit (`run-baseline`); the others are organiser-produced (GPU / PyKEEN / sentence-transformers /
LogMap / Soufflé) and ship as prediction files:

- `exact_lexical`, `word_embedding_based` (all-MiniLM-L12-v2 cosine), the KGE family (`transe`,
  `distmult`, `complex`, `rotate`; PyKEEN, dim 128, ≤ 50 epochs);
- `logmap` — LogMap 4.0 MATCHER on the full ontologies, confidence for returned typed mappings and
  −1.0 otherwise. Its SNOMED-FMA run did not finish within the 4 h limit, so it returns nothing on
  SNOMED-FMA and that row is the scorer's tie order;
- `text_ranker_minilm` — frozen all-MiniLM-L12-v2 class embeddings + a trained relation head;
  `text_ranker_minilm_reach` / `_closure` — the same plus OWL 2 RL support from named-class
  reachability / the full released closure over the public train mappings (weight chosen on
  validation);
- `cross_encoder_minilm` — fine-tuned ms-marco-MiniLM-L-12-v2 with a three-relation head.
